# PrAImate 1.0 — GUI, Rebrand, Unified Backend Plan

**Status:** Draft for execution
**Decision date:** 2026-06-10
**Author:** clade-dev session

This document supersedes any prior brainstorming. It is the contract for delivering PrAImate 1.0. Phases are ordered, each with a hard gate. No phase starts until the previous one passes its gate.

---

## 0. Decisions (locked)

| # | Decision | Choice |
|---|---|---|
| 1 | DB encryption | **None** in 1.0. Plain SQLite. Encryption deferred to a later major. |
| 2 | SQLite driver | **`modernc.org/sqlite`** — pure Go, no cgo, preserves the single-binary policy. |
| 3 | Agents portability | **YAML files**, import/export from both CLI and GUI. DB is the runtime store; YAML is the wire format. |
| 4 | Workflow execution | **Option (b)** — PrAImate-level scripted multi-turn through the CLI agent. Gives cross-CLI compatibility (same agent runs on Claude / Codex / OpenCode / etc.). |
| 5 | GUI frontend | **SvelteKit** with Wails v3 bindings. |
| 6 | Rebrand timing | **From the start.** PrAImate 1.0 is a fresh release. No "update from clade" path. |
| 7 | Old data migration | **None.** Users reinstall as a new app. Old `~/.clade/` is ignored — they keep it or delete it themselves. |
| 8 | Settings sharing CLI↔GUI | **Not shared.** Each UI has its own settings tab and its own settings rows. Shared data is only chats, agents, memory, MCP catalogue. |
| 9 | Fork OpenCode as base | **No.** Use it as visual/UX reference only. See section 10 for the full rationale. |

## 1. Target architecture

```
┌──────────────────────────────────────────────────────────┐
│   cmd/praimate (TUI)       cmd/praimate-gui (Wails)      │
└──────────────┬───────────────────────┬───────────────────┘
               │                       │
┌──────────────▼───────────────────────▼───────────────────┐
│  internal/core    (single API surface for both UIs)      │
│  ┌────────────────────────────────────────────────────┐  │
│  │  Chats · Agents · Memory · MCP · Schedules ·       │  │
│  │  Watchers · Privacy · Launch · Workflows           │  │
│  └────────────────────────────────────────────────────┘  │
├──────────────────────────────────────────────────────────┤
│  internal/store  (single SQLite at ~/.praimate/db.sqlite)│
├──────────────────────────────────────────────────────────┤
│  internal/launcher    (existing — refactored)            │
│  internal/ollama · internal/installer · internal/updater │
└──────────────────────────────────────────────────────────┘
```

**Iron rules:**
- `cmd/*` may only call `internal/core`. Never opens the DB. Never imports `internal/launcher` directly.
- Only `internal/store` opens the SQLite file. Everything else uses typed query methods.
- `internal/core` is the public API for both UIs. New features land here first, then UIs surface them.
- TUI and GUI are equal citizens. No "GUI-only" features. Anything Wails can do, the TUI can also drive (even if the affordance is uglier).

## 2. File system layout (PrAImate 1.0)

```
~/.praimate/
  db.sqlite              # single source of truth for chats, agents, memory, MCP, schedules
  db.sqlite-wal          # WAL
  agents/                # exported agent YAML files (user-managed)
  chats/                 # transcript slices (large blobs) - DB references by path
  cache/                 # installer downloads, model probe results
  logs/
    praimate.log
    gui.log
```

Reasoning for keeping transcript slices outside the DB: they're large (often MB-scale per chat), append-only, and we already mirror them; storing them as files lets us tail-stream them efficiently without DB I/O and lets users rotate / archive them by hand.

## 3. Database schema (v1)

`internal/store/migrations/0001_init.sql`:

```sql
CREATE TABLE chats (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  agent_id TEXT,                   -- nullable: ad-hoc chats have no agent
  cli_agent TEXT NOT NULL,         -- "claude" | "codex" | "opencode" | "deepseek" | "gemini"
  workspace_path TEXT,             -- working folder
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  ended_at TEXT,                   -- NULL while running
  exit_kind TEXT,                  -- "completed" | "cancelled" | "over_budget" | "agent_crashed" | "external_kill"
  settings_json TEXT NOT NULL DEFAULT '{}'
);

CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id TEXT NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
  ts TEXT NOT NULL,
  role TEXT NOT NULL,              -- "user" | "assistant" | "tool" | "system"
  content TEXT NOT NULL,
  tokens INTEGER,
  meta_json TEXT NOT NULL DEFAULT '{}'
);

CREATE TABLE agents (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  description TEXT NOT NULL DEFAULT '',
  icon TEXT,
  instructions TEXT NOT NULL DEFAULT '',
  tools_json TEXT NOT NULL DEFAULT '[]',
  mcp_servers_json TEXT NOT NULL DEFAULT '[]',
  workflows_json TEXT NOT NULL DEFAULT '[]',
  supports_json TEXT NOT NULL DEFAULT '[]',  -- which CLI agents this works on
  source_path TEXT,                          -- original YAML on disk if imported
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE memory_identity (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL,
  source TEXT NOT NULL,            -- "manual" | "derived"
  updated_at TEXT NOT NULL
);

CREATE TABLE memory_pinned (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  text TEXT NOT NULL,
  salience REAL NOT NULL DEFAULT 0.5,
  source_count INTEGER NOT NULL DEFAULT 1,
  use_count INTEGER NOT NULL DEFAULT 0,
  last_used TEXT,
  created_at TEXT NOT NULL,
  last_decayed_at TEXT NOT NULL
);

CREATE TABLE memory_episodes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id TEXT REFERENCES chats(id) ON DELETE SET NULL,
  summary TEXT NOT NULL,
  topics_json TEXT NOT NULL DEFAULT '[]',
  entities_json TEXT NOT NULL DEFAULT '[]',
  decisions_json TEXT NOT NULL DEFAULT '[]',
  actions_json TEXT NOT NULL DEFAULT '[]',
  salience REAL NOT NULL DEFAULT 0.5,
  created_at TEXT NOT NULL
);

CREATE TABLE mcp_servers (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  transport TEXT NOT NULL,         -- "stdio" | "http" | "sse"
  command TEXT,                    -- for stdio
  url TEXT,                        -- for http/sse
  args_json TEXT NOT NULL DEFAULT '[]',
  env_json TEXT NOT NULL DEFAULT '{}',
  auth_json TEXT NOT NULL DEFAULT '{}',  -- oauth tokens / api keys
  enabled INTEGER NOT NULL DEFAULT 1,
  catalogue_key TEXT,              -- "linear" | "notion" | ... NULL for custom
  created_at TEXT NOT NULL
);

CREATE TABLE schedules (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id TEXT REFERENCES chats(id) ON DELETE CASCADE,
  agent_id TEXT REFERENCES agents(id) ON DELETE CASCADE,
  cron TEXT,                       -- standard cron expr OR
  at TEXT,                         -- ISO timestamp for one-shot
  workflow TEXT,
  inputs_json TEXT NOT NULL DEFAULT '{}',
  on_miss TEXT NOT NULL DEFAULT 'skip',  -- "skip" | "run_once" | "run_catchup"
  priority TEXT NOT NULL DEFAULT 'normal',
  last_run_at TEXT,
  next_run_at TEXT,
  enabled INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE watchers (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id TEXT REFERENCES chats(id) ON DELETE CASCADE,
  agent_id TEXT REFERENCES agents(id) ON DELETE CASCADE,
  path TEXT NOT NULL,
  patterns_json TEXT NOT NULL DEFAULT '[]',
  workflow TEXT,
  inputs_json TEXT NOT NULL DEFAULT '{}',
  debounce_ms INTEGER NOT NULL DEFAULT 1000,
  enabled INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE settings_cli (
  key TEXT PRIMARY KEY,
  value_json TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE settings_gui (
  key TEXT PRIMARY KEY,
  value_json TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE schema_version (version INTEGER PRIMARY KEY);
INSERT INTO schema_version VALUES (1);
```

**Why two settings tables, not one:** the CLI and the GUI surface different controls (TUI has keybindings, mouse-mode, colour palette; GUI has window size, theme, sidebar width, notification preferences). A shared table would force fake "ui_mode" prefixes on every key and would make it tempting to leak GUI-only state into TUI startup paths. Keep them physically separate.

**What IS shared across UIs:** `chats`, `messages`, `agents`, `memory_*`, `mcp_servers`, `schedules`, `watchers`. Both UIs read and write these. A chat started in the TUI shows up in the GUI sidebar with the same ID, same transcript, same exit code. Memory accumulated through TUI chats is visible to GUI-launched chats. Same for agents and MCP servers.

`internal/store` runs migrations on first open; new migrations append-only as `0002_*.sql`, never edit a shipped one.

## 4. Agent file format (portable YAML)

`~/.praimate/agents/my-coding-buddy.yaml`:

```yaml
schema: praimate.agent/v1
id: my-coding-buddy
name: My Coding Buddy
description: General-purpose coding assistant with strict TDD discipline.
icon: laptop

# System prompt — becomes the first message to the CLI agent.
instructions: |
  You are a TDD-disciplined coding assistant.
  Always write the failing test before the implementation.
  Cite file:line for every claim about the codebase.

# Which third-party CLIs this agent can run on. PrAImate will refuse to launch
# the agent through a CLI not in this list.
supports:
  - claude
  - codex
  - opencode

# Tool toggles. These map to the CLI agent's tool catalogue at launch time;
# unsupported tools are quietly dropped per-CLI.
tools:
  - file_read
  - file_write
  - file_search
  - shell_run
  - git

# MCP servers this agent wants enabled. Refer to entries in the user's MCP
# catalogue by id; PrAImate writes the per-CLI config before launch.
mcp_servers:
  - linear
  - github

# Workflows: named task templates. Each is a multi-turn scripted execution
# through the CLI agent (decision 4 = option b).
workflows:
  - name: Triage Issue
    description: Reads a GitHub issue, proposes a plan, opens a PR draft.
    inputs:
      - name: issue_url
        prompt: GitHub issue URL
        type: string
        required: true
    steps:
      - kind: user_message
        template: |
          Read this issue: {{ .issue_url }}
          Summarise it in 3 bullets, list affected files, propose a plan.
      - kind: wait_for_assistant
      - kind: user_message
        template: |
          Implement the plan. Open a draft PR when done.
      - kind: wait_for_assistant
        until_tool: complete

  - name: Freeform
    description: Just ask a question.
    inputs:
      - name: task
        prompt: What do you want to do?
        type: text
        required: true
    steps:
      - kind: user_message
        template: '{{ .task }}'
      - kind: wait_for_assistant
        until_tool: complete

# Default workflow used when the user just hits "launch" without picking one.
default_workflow: Freeform
```

**Workflow step kinds (v1):**
- `user_message` — render `template` with input substitution, send as next user turn.
- `wait_for_assistant` — block until the CLI agent emits a turn. Optional `until_tool: <name>` to wait for a specific tool call (`complete`, `clarify`, etc.).
- `if` / `else` — branch on prior turn content (regex match, JSON path).
- `loop` — repeat a sub-sequence until condition met.

`if` / `else` / `loop` ship in 1.1, not 1.0. v1 supports linear scripts only — enough to express "ask the user for input → send it → wait → done."

## 5. Phases

Each phase is independently shippable. Hard gate after each.

### Phase 0 — Repo scaffold + decisions doc (0.5 day)

- Create new git repo `github.com/sPROFFEs/PrAImate` (or branch in current repo named `praimate-1.0`).
- Copy `internal/launcher`, `internal/ollama`, `internal/installer`, `internal/updater` from Clade. Rename module path to `github.com/sPROFFEs/PrAImate`.
- Top-level `cmd/praimate/main.go` stub that prints `PrAImate 1.0-dev`.
- Add `clade` shim build target that prints "clade has been replaced by praimate — see https://...". This is the *only* concession to old users.
- Land this doc to `knowledge/1.0-plan.md` in the new repo.

**Gate:** `go build ./...` succeeds. Old Clade tests run unchanged.

### Phase 1 — `internal/store` + `internal/core` skeleton (1.5 days)

- `internal/store` package:
  - Open `~/.praimate/db.sqlite` via `modernc.org/sqlite`.
  - Run migrations from embedded `migrations/*.sql`.
  - Typed query methods (hand-rolled, not sqlc — keeps the dep count low).
  - `store.Open(path string) (*Store, error)`, `store.Close()`.
- `internal/core` package:
  - `core.New(store *Store, ...) *Core` constructor.
  - Method stubs for every operation the TUI currently performs: `ListChats`, `CreateChat`, `LaunchChat`, `ListAgents`, `ImportAgent`, etc.
  - Each stub currently delegates to the existing `internal/launcher` functions.
- TUI (`cmd/praimate`) now calls `core` exclusively for chat list / launch. No more direct `launcher.LoadChats()`.

**Gate:** TUI launches, lists chats, runs a chat through Claude Code end-to-end. All existing tests pass after the refactor.

### Phase 2 — Agents (the new abstraction) (2 days)

- YAML parser + validator for the agent format above.
- `core.ImportAgent(path string)`, `core.ExportAgent(id, path string)`.
- Agents stored in DB; YAML is wire format.
- New TUI screen `screen_agents.go`: list agents, view, import, export, delete, create-from-template.
- Built-in agents shipped in `assets/agents/`:
  - `freeform.yaml` — single freeform input.
  - `tdd-coder.yaml` — TDD discipline.
  - `release-engineer.yaml` — PrAImate's own release pipeline as an agent (dogfooding).
- Launch flow update: pick CLI → pick agent (optional) → if agent has workflows, pick one → fill inputs → launch.
- Engine `internal/core/workflow.go` runs the linear script: renders `user_message` templates, pipes to CLI stdin, scans transcript for `wait_for_assistant` completion.

**Gate:** Launch a chat from the built-in `tdd-coder` agent with input. Confirm the rendered first turn lands in the CLI agent. Confirm `Freeform` agent matches today's launch UX.

### Phase 3 — Memory (3 days)

- Implement M1–M5 from prior discussion against the schema in section 3:
  - Identity row + manual TUI screen ("Me").
  - Per-chat episode distillation: `tea.Cmd` with 60s debounce after last message; on fire, one LLM call to the chat's configured endpoint (ollama or cloud), parsed as JSON into an episode row.
  - Promote pinned: nightly job — if a fact text appears in ≥3 recent episodes, promote.
  - Decay job: on PrAImate startup, if `now - last_decay > 7d`, run `salience *= exp(-Δdays / 30)` across `memory_pinned`.
  - Retrieval planner: classify the user's first message of a new chat, inject identity + at most one episode + top pinned facts within an 800-token budget.
  - Byte-stable compaction watermark for slice files.
  - Exit taxonomy populated on every chat end.
- New TUI screen `screen_memory.go`: browse identity, pinned facts (sortable by salience), episodes (sortable by date). Edit / delete buttons.
- Memory injection is **opt-in per chat** via a settings toggle. Default off in 1.0 so we don't surprise users.

**Gate:** Manual smoke: have a chat where I tell PrAImate my name. Start a new chat with memory on. Confirm name surfaces in the injected context. Decay job runs on second startup.

### Phase 4 — Tier A polish (3 days)

Sequential, each ~0.5–1 day:

- **MCP catalogue:** Hard-coded list of ~25 known providers (Linear, Notion, GitHub, Vercel, Supabase, Sentry, Stripe, Cloudflare, …). One-tap connect: paste API key or run OAuth 2.1 + DCR (use `golang.org/x/oauth2`). On agent launch, PrAImate writes the per-CLI MCP config (`~/.codex/`, `~/.claude/`, etc.) for the servers the agent declares.
- **Folder watchers:** `fsnotify` per chat. On debounced change matching `patterns_json`, fire the configured workflow.
- **Scheduled re-runs:** `robfig/cron/v3`. Scheduler daemon goroutine inside PrAImate when the app is running; not a separate cron daemon (yet — could be in 1.1).
- **Privacy redaction pre-send:** regex tier only (SSN / CC / IBAN / AWS keys / GH tokens / custom user patterns). TUI shows a review sheet when matches found before sending.
- **Voice / App Intents / Sandbox VM:** all explicitly out of scope for 1.0.

**Gate:** Each feature has at least one regression test. Manual smoke for each.

### Phase 5 — GUI MVP (Wails + SvelteKit) (5 days, can overlap Phase 4)

Project layout:
```
cmd/praimate-gui/
  main.go              # Wails bootstrap, binds core
  bindings/            # Go methods exposed to JS
  app.go               # Wails App struct
frontend/
  src/
    routes/
      +layout.svelte           # sidebar shell
      +page.svelte             # home / chat list
      chat/[id]/+page.svelte   # live chat
      agents/+page.svelte      # agent catalogue
      memory/+page.svelte      # memory inspector
      mcp/+page.svelte         # MCP catalogue
      settings/+page.svelte    # local LLM, privacy, schedules, watchers
    lib/
      components/    # AgentCard, ChatStream, MemoryRow, MCPCatalogueItem
      api.ts         # thin wrapper over Wails bindings
      stores.ts      # Svelte stores for chats, agents, etc.
  static/
  svelte.config.js
  vite.config.js
  package.json
```

**Aesthetic direction:** inspired by Osaurus — sidebar of agents (each with icon + colour), main column chat panel (markdown-rendered, streaming), right column for memory / tools inspector. Dark theme primary; light secondary. Use **xterm.js** for the live CLI stream (gives users a real terminal view of what the agent is doing). Fonts: Inter for UI, JetBrains Mono for code.

**Wails bindings (Go → JS):**
- `ListChats() []Chat`
- `CreateChat(req CreateChatRequest) Chat`
- `LaunchChat(id string) (stdoutChannel string)`  → streams via Wails events
- `ListAgents() []Agent`
- `ImportAgent(path string) Agent`
- `ExportAgent(id, path string)`
- `RunWorkflow(chatID, workflowName string, inputs map[string]string)`
- `GetMemory() MemorySnapshot`
- `ListMCP() []MCPServer`
- `ConnectMCP(catalogueKey string) (oauthURL string)`
- `Settings*()` for each settings section

All bindings hit `internal/core`. **Zero duplicated business logic.** The GUI is a presentation layer.

**Distribution:** `praimate-gui` binary embeds the built Svelte frontend via `embed.FS` and Wails's asset handler. Single ~30 MB binary per OS. Linux uses webkit2gtk; macOS uses WebKit; Windows uses WebView2 (system-provided).

**Gate:** End-to-end: open GUI → import agent YAML → create chat against Claude Code in a working folder → see streaming output → chat persists to same DB the TUI reads → kill GUI, open TUI, resume the same chat.

### Phase 6 — Release (1 day)

- `internal/version/version.go` → `Current = "1.0.0"`, `Name = "PrAImate"`.
- `scripts/build.sh` builds two binaries per target: `praimate` (TUI) and `praimate-gui` (Wails). Five OS targets each = 10 archives.
- `scripts/build.ps1` same for Windows.
- Wails frontend build is part of `build.sh`: `cd frontend && pnpm install && pnpm build`, then `wails build` per target.
- README rewrite: PrAImate as the brand; describe both `praimate` and `praimate --gui` (or `praimate-gui`) entrypoints; install via `go install`, prebuilt archives, or homebrew (future).
- `knowledge/architecture.md` updated for the new package map.
- Release pipeline: same shape as Clade's `release X.Y.Z` flow, but with the 10-archive matrix.

**Gate:** Fresh VM install of each release archive works. `praimate -version` prints `1.0.0`. `praimate-gui` opens a window. Both share `~/.praimate/db.sqlite`.

## 6. What we are explicitly *not* doing in 1.0

Spelled out so future-us doesn't quietly add them:

- No data migration from `~/.clade/`. Old users reinstall.
- No DB encryption.
- No voice input (FluidAudio / Whisper).
- No on-device privacy classifier (MLX). Regex tier only.
- No sandbox Linux VM. We continue trusting the user's shell.
- No cryptographic identity (secp256k1) / Relay tunnels / portable access keys.
- No App Intents / Spotlight / Siri / global hotkey.
- No plugin v3 host API (no in-app HTTP routes, no embedded SQLite for plugins).
- No `if` / `else` / `loop` workflow step kinds — linear scripts only.
- No catch-up of missed schedules across PrAImate restarts (only while running).
- No telemetry. No crash reporting.

Each of these is a defensible 1.1+ feature; just not in scope now.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| `modernc.org/sqlite` is slow on huge writes | Transcript slices stay outside the DB; only metadata + memory rows hit SQLite. Bench at end of Phase 3. |
| Wails 1.0 frontend rot (vite/svelte/node toolchain churn) | Pin `package.json` versions exactly. CI uses `pnpm install --frozen-lockfile`. |
| Linux GUI needs webkit2gtk runtime | Document the apt/dnf install in README. Provide an AppImage in 1.1 to bundle it. |
| Workflow option (b) is harder than option (a) | Phase 2 implements only the linear script kinds; conditionals and loops deferred. If even linear is too much, fall back to (a) for 1.0 and ship (b) in 1.1. Decide at Phase 2 mid-point. |
| Per-CLI tool name divergence breaks `tools:` lists | Maintain a per-CLI tool-name map in `internal/core/cli_tools.go`. Unknown tools silently dropped with a warning in the launch log. |
| Memory distillation costs tokens on cloud models | Make distillation endpoint per-chat (default: same endpoint as the chat). Provide an Ollama fallback toggle. |
| Frontend "looks like Osaurus" without literally cloning it | Use Osaurus as visual reference, write all components from scratch. Avoid lifting any of their SwiftUI source or assets. |

## 10. Why we are NOT forking OpenCode

The pitch: "OpenCode (sst/opencode, MIT) already has a TUI + desktop app + web UI + multi-provider agent loop — fork it, tweak it, ship it as PrAImate. Massive head start."

The pitch is tempting but wrong for our goals. Five reasons, in order of importance:

### 10.1 It changes what PrAImate IS

The PrAImate vision locked in sections 1–4 is a **harness**: a launcher that wraps third-party CLI agents (Claude Code, Codex CLI, OpenCode CLI, Gemini CLI, DeepSeek-TUI) behind one TUI/GUI plus shared agents/memory/MCP. The user runs *their preferred coding agent* through us; we add the surrounding layer.

Forking OpenCode would make PrAImate **its own coding agent** — one that competes with the very CLIs we currently wrap. We would still need to keep wrappers for Claude/Codex/Gemini for users who prefer them, but we would now also maintain our own agent loop. That is two products in one binary.

The "harness" framing is what differentiates PrAImate from Osaurus, from OpenCode itself, from Cursor, from every other AI coding tool. Forking dilutes it.

### 10.2 Stack contradiction

OpenCode is **68.6% TypeScript** + Bun runtime + SST infra + Turbo monorepo. Its TUI is the only Go piece, and the TUI delegates to the TypeScript server for the actual agent loop.

Adopting that stack means PrAImate gains a hard runtime dependency on Bun (or Node) and a TypeScript codebase to maintain alongside Go. That kills the single-binary policy (decision 2 above is meaningless if half the app is TypeScript). It also doubles the toolchain we ship to contributors.

PrAImate's Go-only constraint is one of its strongest invariants — it's why the binary is 10 MB and `go install` works. Forking OpenCode trades that away for code we mostly didn't want anyway.

### 10.3 Permanent upstream divergence cost

A fork that diverges from upstream pays a tax forever. Every OpenCode release we want a feature from = a port. Every OpenCode security fix = a port. After 6 months we've either drifted so far that ports are infeasible (and we're maintaining a hard fork of a 100k-LOC codebase) or we've kept up and our "tweaks" are constantly broken by rebase.

We are a one-maintainer project. We cannot afford that tax.

### 10.4 Brand-strip surface area

Stripping OpenCode's brand is non-trivial: hundreds of string literals, asset files, telemetry endpoints, MCP server names, error messages mentioning "OpenCode", `sst/opencode` URLs in docs. Plus their telemetry stack (if any) needs to be removed cleanly. This is a week of work that produces zero user-visible value.

### 10.5 The "head start" is smaller than it looks

What OpenCode actually gives us if we fork:
- Multi-provider routing — we already do this via the CLI agents themselves.
- TUI — we already have one, in idiomatic bubbletea Go.
- Web UI — yes, but ours is Wails-desktop, not web-server. Different category.
- Agent loop — we explicitly DON'T want our own, per 10.1.
- Tool catalogue — useful, but every CLI we wrap brings its own.

The net new thing we'd inherit is **their web UI design**, which is what we actually wanted in the first place. And design we can copy with our eyes — we don't need their code.

### 10.6 What we DO take from OpenCode (MIT, fair game)

- **Read their TUI Go code (`packages/tui/`) for bubbletea patterns** — chat-stream rendering, multi-pane layouts, keybinding affordances. Their TUI is well-engineered; we can learn from it without forking.
- **Read their web UI source for visual layout, component hierarchy, colour choices.** Reproduce in SvelteKit.
- **Read their agent definition format (`opencode.json` schema, agent files).** Cross-check against our YAML format; steal good ideas.
- **Read their MCP integration code** for OAuth flow patterns.

All of this is "read, learn, reimplement" — not "fork." Their MIT license permits direct lifting too, but the maintenance argument (10.3) holds whether we lift or rewrite.

### 10.7 Recommendation

- Keep PrAImate as a harness. Ship the plan in sections 1–9 unchanged.
- Add OpenCode to a `references/` doc in the repo: list which OpenCode files we studied, what we borrowed conceptually, and link to upstream. This honours MIT attribution and gives future contributors a paper trail.
- If 1.0 ships and the harness model proves to have a ceiling, revisit forking in a 2.0 conversation — by then we'll know what's actually missing.

## 13. Additions — reviewed improvements deferred by cost

Logged during the Phase 5 code-review pass. Each is worth doing but
costs more than its value *right now*; pull them into 1.0.x / 1.1
milestones deliberately.

### 13.1 Wails v3 migration (deviation: shipped on v2)
Plan said "Wails v3"; v3 is still alpha and its API churns. Shipped on
v2.10.2 (stable, identical capability for our surface). Revisit when
v3 hits RC — the binding layer is one file (`app.go`), so the port is
mechanical.

### 13.2 SvelteKit (deviation: shipped Svelte 4 + Vite SPA)
Kit's file routing and SSR add nothing inside a desktop webview and
add a toolchain layer that breaks more often. The SPA keeps the same
component layout as the planned Kit routes (`src/pages/*` ≈
`src/routes/*`). If a hosted web deployment ever matters, migrate then.

### 13.3 TUI still imports internal/launcher directly (iron-rule debt)
`cmd/praimate` screens (chats list, templates, install, local-llm)
still call `internal/launcher` directly instead of going through
`internal/core`. The GUI is fully compliant; the TUI predates the rule.
Refactor cost: ~2 days of mechanical facade work, zero user-visible
change. Do it before any second backend consumer appears.

### 13.4 Only the Claude adapter is registered
`CLIAdapter` exists for exactly one CLI. Codex (`codex exec`),
OpenCode (`opencode run`), Gemini — each needs a ~150-line adapter +
parser tests. Until then agents declaring `supports: [codex]` fail at
launch with "no CLI adapter registered". High user value; medium cost
(verify each CLI's headless flags + session-resume story).

### 13.5 Live PTY streaming / xterm.js
Current streaming is turn-granular (one event per completed turn).
Real-time token/tool streaming needs PTY capture of the child CLI and
an xterm.js pane — meaningful work in both the runner and frontend.
Worth it for long agentic runs where users currently stare at a
spinner; pair with run-cancellation (the context plumbing exists).

### 13.6 Chat resume from GUI/TUI chat list
`chats` rows store the adapter `SessionID`, so "continue this
conversation" is feasible via `adapter.Resume`. Needs a new core
method (`ContinueChat(chatID, message)`) + UI affordances. Natural
1.0.x follow-up.

### 13.7 Schedules on_miss semantics
`run_once` / `run_catchup` are stored but the daemon treats everything
as `skip` (one dispatch per due row while the app runs). Implementing
catch-up needs persisted tick bookkeeping. Explicitly out of 1.0 scope
(§6) — keep it there.

### 13.8 Frontend CI + lockfile
Commit `package-lock.json`, add a CI job: `npm ci && npm run build`
plus `go vet -tags webkit2_41 ./cmd/praimate-gui`. Stops frontend rot
(risk table §7) from landing silently.

### 13.9 GUI run history dedup
`RunWorkflow` returns the full turn list AND the turns were already
streamed as events; the Run page renders whichever arrived. Harmless
duplication on the wire — could slim the result payload to outcome +
chat_id once the Chats page can render the persisted transcript
immediately after a run.

### 13.11-design Unified Agents — fold Templates into Agents (1.1 headline)

User-reported confusion (2026-06-10): post-1.0 PrAImate carries two
overlapping concepts — **Templates** (on-disk workpath bundles:
mission/playbook/rules/tools, wpc-compiled into a per-chat sandbox;
the original Clade model) and **Agents** (DB-stored YAML:
instructions/workflows/inputs/MCP; the 1.0 model). They should merge.

Design sketch:
- `Agent` gains an optional `workpath:` field — either a path to a
  template directory or an inline-embedded bundle. Launching such an
  agent = clone/compile the workpath into the chat sandbox (existing
  wpc flow) + drive the CLI there with the agent's instructions and
  workflow. Agents without `workpath:` behave as today.
- The Templates tab disappears; "new chat" starts from an agent.
  Existing templates auto-wrap into generated agents on first launch
  (one agent per template, freeform workflow).
- Sample templates ship as sample agents.

Blast radius: chats/templates screens, wpc compile flow, samples
seeding, resume logic — ~3-5 days. Too large to slip into 1.0.x as a
patch; do it as the 1.1 headline with a migration note. Until then
the two tabs coexist.

### 13.12-DONE PrAImate Code — bundled rebranded OpenCode (shipped)

The maintainer chose the fork-embed path explicitly (accepting the
binary size). Implemented as a version-pinned, rebranded build of
OpenCode shipped as a sibling binary (`praimate-code`), dispatched via
`praimate code` — the same proven pattern as `--gui`, so the lean TUI
binary isn't bloated but `praimate code` still works out of the box.

- `scripts/build-praimate-code.sh`: clones OpenCode at a pinned tag

  a ~150MB self-contained `praimate-code`. Preserves OpenCode's MIT
  LICENSE + writes a NOTICE recording upstream + commit (MIT requires
  retaining the copyright notice; we rebrand the product NAME only).
  Proven end-to-end: built, smoke-tested (--version), dispatched.
- `scripts/praimate-code-rebrand.sh`: conservative name-level rebrand
  seam. Deliberately does NOT blind-sed internal identifiers / config

  rebranding is incremental follow-up.
- `cmd/praimate/code_run.go`: `praimate code [args]` resolves

  install.ps1 put it on PATH when the archive carries it; gitignored

### 13.12-rejected-design "praimate-code" — embedding rationale (superseded by 13.12-DONE)

Request (2026-06-10): clone the OpenCode repo, rebrand it
`praimate-code`, and ship it *inside* the PrAImate binary so users
get a stable, zero-install coding CLI managed by us.

Why embedding cannot work as asked:
- OpenCode is TypeScript on Bun. "Inside our binary" means embedding
  a JS runtime (~50-90 MB per platform) plus their bundle, extracted
  at first run — the binary balloons past 100 MB and we become
  shippers and maintainers of a JS runtime. This violates the
  single-binary Go policy more thoroughly than anything in §10.2.
- All of §10.3 (permanent divergence tax) and §10.4 (brand-strip
  surface) apply in full, *plus* we'd own the support surface for
  someone else's agent loop under our name.

Counter-proposal that delivers the actual user value ("a stable CLI
that works out of the box, managed by us") at ~5% of the cost:
- **Managed, version-pinned OpenCode install.** Reuse the existing
  managed-agent machinery (`installer.ManagedAgentPrefix`, the same
  flow that installs openclaude into
  `<config>/praimate/agents/<name>/`): PrAImate offers "Install
  praimate-managed OpenCode (vX.Y.Z)" in the Agents/CLIs tab; we pin
  a vetted version, smoke-test it against our launcher before

## 14. Live Markdown co-editing studio (planned — next GUI headline)

Requested 2026-06-12. The idea: a **document-editor agent experience**
in the GUI. The user opens a "doc editor" agent and PrAImate opens a
dedicated editor **window** — multi-tab, multi-file — where the user
and the model edit the same `.md` files **in real time**: the user
types directly in the editor, prompts the agent from an attached chat
pane, and watches the agent's edits land live in the open tabs. The
agent works with the user's prompts plus its knowledge base
(instructions + any knowledge files the agent declares).

### 14.1 Concept and UX contract

- **Entry point:** an agent flagged `editor: true` (or a "Open in Doc
  Studio" action on any chat). Opening it spawns the editor window
  scoped to a folder — the chat's workspace by default — with a file
  tree, tabbed editors, and the existing chat composer (streaming,
  Tools levels, attachments, `!commands`) docked beside the document.
- **Both sides edit, all the time.** User keystrokes are never locked
  out while the agent runs. Agent edits appear as live updates in the
  open tab (cursor-stable merge, not a whole-buffer reload), visually
  attributed (flash/gutter mark on agent-changed lines, like a
  collaborator's presence in Google Docs).
- **The documents the model sees are the documents on screen.** Every
  prompt automatically carries the focused file (and the open-tab
  list) as context; the agent's knowledge base rides along via the
  existing system-prompt + attachments machinery. No copy-pasting
  markdown into chat.
- **Markdown-first**: rendered/WYSIWYG editing with a source toggle.
  Plain `.txt`/code files open in source mode. Preview pane optional.

### 14.2 Editor technology — open-source survey and pick

Surveyed options for the embedded editor component ("which are
available open-source… maybe tiny?"):

| Candidate | License | Verdict |
|---|---|---|
| **TinyMCE** ("tiny") | GPLv2+ / commercial since v7 | **No.** HTML-WYSIWYG at heart (markdown is a bolt-on), heavyweight, and the GPL/commercial dual license is a distribution headache for an MIT-ish app. |
| **CodeMirror 6** | MIT | **Yes — the core pick.** Best-in-class plain-text/markdown editing, tiny, framework-agnostic (fits our Svelte 4 SPA), first-class collaborative-editing support via `y-codemirror.next`, and it handles *external document changes without losing the user's cursor* — the property this whole feature hinges on. |
| **Milkdown** | MIT | **Yes — as the WYSIWYG layer.** Markdown-native WYSIWYG built on ProseMirror, plugin-based, Yjs collab plugin available. Pairs with CodeMirror as the rendered view ↔ source view toggle. |
| Tiptap | MIT core | Solid ProseMirror alternative to Milkdown; markdown via extensions rather than native — second choice. |
| Monaco | MIT | VS Code's editor; heavyweight, code-oriented, poor mobile/webview ergonomics — overkill for prose. |
| BlockNote | MPL-2.0 | Notion-style blocks, React-centric — wrong framework for us. |
| **Yjs** (glue, not an editor) | MIT | **Yes.** The de-facto CRDT layer: one shared `Y.Doc` per file, editor bindings for both CodeMirror and Milkdown/ProseMirror, so user edits and agent-originated updates merge conflict-free in real time. |

Pick: **CodeMirror 6 + Milkdown, glued by Yjs** — all MIT, all
embeddable in the existing Svelte frontend, no new runtime.

### 14.3 Architecture, the real-time trick, and phasing

**Disk is the shared truth — that's what makes "model edits live" work
with the harness model.** The wrapped CLIs already edit files (Tools
level "edits"/"full", or per-edit "Ask" approvals); they cannot speak
an editor protocol, and they don't need to:

```
user keystrokes ──► Y.Doc ──debounced──► file on disk ──► next agent turn reads it
agent file edit ──► fsnotify ──► diff vs Y.Doc ──► CRDT update ──► open tab updates live
```

The editor backend (Go) holds one `Y.Doc` per open file, watches the
scoped folder with the existing fsnotify machinery, converts external
writes into minimal text deltas (diff-match-patch) applied to the
Y.Doc — so the user's cursor and unsaved edits survive — and flushes
user edits to disk with a short debounce + conflict-safe write. The
agent "collaborates" at sub-second file granularity, which reads as
real time in the tab; true keystroke-level co-typing is impossible
through the CLI boundary anyway and not needed.

**Window strategy (the one real constraint):** Wails **v2 cannot open
a second window**. Two options, in preference order:
1. **Second process, same binary** — `praimate-gui -editor <folder>`
   (the `-mcp-approve` hidden-mode pattern we already ship). The
   editor process opens its own Wails window and talks to core
   directly (same DB, same adapters); chat state stays consistent
   because chats are DB rows. Ship-now cost, no framework risk.
2. **Wails v3 multi-window** — revisit when v3 reaches RC (§13.1);
   collapses the two processes into one.

**Phasing:**
- **14-P1** — editor window (separate process), file tree + tabs,
  CodeMirror source editing, fsnotify live-merge of agent edits, chat
  pane wired to the existing streaming/approvals stack. Gate: user and
  agent alternate edits on the same open file with zero lost
  keystrokes and zero whole-buffer reloads.
- **14-P2** — Milkdown WYSIWYG toggle, agent-edit attribution
  (gutter/flash), open-tabs context injection, knowledge-base panel.
- **14-P3** — multi-file agent operations (rename/create/delete
  reflected in the tree live), per-tab Ask-level approvals, optional
  Yjs websocket so a future praimate-web can join the same session.

Out of scope here: real multi-user collaboration (two humans), CRDT
persistence across restarts (disk is persistence), and non-markdown
rich formats (docx etc. — attachments already cover reading them).
